PLATFORM · COST + LINEAGE

What every number costs, and where it came from.

Two questions a platform team gets asked every week. Here dbt answers both: cost models read warehouse metering, query attribution and dbt run history, and the lineage graph comes straight from dbt's manifest. The cost data is invented and shaped like Snowflake's usage views, so this runs on DuckDB with no account.

01 / COST TRACKINGBudget, burn and attribution

Spend against budget.

Each workload runs on its own warehouse behind its own resource monitor, so one runaway job cannot spend another team's credits. Status follows the monitor's triggers: notify at 75%, suspend at 100%. The forecast is a straight-line run rate to the month end.

ATTRIBUTION BY USER

Who spent it

Each workload logs in as its own service user, so query attribution names a team rather than a shared admin role. Idle time is never attributed, so these add up to less than metered compute.

COST BY DBT MODEL

What each model costs to build

Daily dbt warehouse credits split across that day's models by execution time. A singular test fails the build if the split stops adding up. Select a model to find it in the lineage.

    03 / IN PRODUCTIONThe same models on Snowflake

    Swap the seeds, keep the models.

    Each invented seed stands in for a real Snowflake source. On a production account the dbt models stay the same and read these instead.

    platform_warehouse_metering→ACCOUNT_USAGE.WAREHOUSE_METERING_HISTORYDaily credits per warehouse; replicates within about 3 hours.
    platform_query_attribution→ACCOUNT_USAGE.QUERY_ATTRIBUTION_HISTORYPer-query compute credits by user; lags up to about 24 hours.
    platform_warehouse_budget→Resource monitor CREDIT_QUOTAMirrored in a reference table, since quotas have no usage view.
    platform_dbt_model_runs→dbt on-run-end hookLogs each model's execution time from run_results.
    dbt manifest.json→ACCESS_HISTORY and OBJECT_DEPENDENCIESAdds run-time reads, including those made outside dbt.
